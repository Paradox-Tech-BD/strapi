Engineering principles and next decision

Phase 2 succeeded by extending native Strapi boundaries rather than introducing a parallel commerce platform.

Decision framePreserve the validated checkout calculation as the system of record; harden its contract before expanding administrative and provider-specific surfaces.
What carries forward

Extend safely, keep the domain native, and prove behavior in a generated Strapi application.

The following principles are the operating model for Phase 3 and future commerce work in this fork.

Keep domain logic native.

Place content types, services, controllers, routes, and lifecycle behavior inside the core ecommerce plugin; keep storefront-specific policies in dependent application extensions.

Register permissions server-side first.

Define valid actions before menu links, pages, and routes rely on them; generated apps must install and enable the server plugin explicitly.

Honor Design System v2 contracts.

Use root imports, accessible roles, Field APIs, and Radix-compatible compound-component composition rather than assuming legacy dialog behavior.

Preserve compatibility deliberately.

Keep legacy service result shapes where existing callers depend on them, while adding currency and exemption details only when checkout context is supplied.

Prefer deterministic evidence.

Use unit, type, build, generated-app E2E, and provider-adapter contract tests; do not make live Stripe or PayPal sandboxes a release gate.

Phase 3 start

Implement checkout input validation and cart/customer integration coverage first; then introduce exemption operations and operational audit/callback seams.
